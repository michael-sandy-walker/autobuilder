  An existing project, adopted, and now asked to change. It was written by someone else and it already
  builds; its existing behaviour is characterised by the tests in src/test/java.
  The change wanted is written in the ticket that asked for it. In the ticket's own words:

    feat(T4-DB): probe creates for success — the ingredient, not another shape

    The 201 abstention was never a missing probe shape. It was one missing
    ingredient: a request body the application will accept. derivedBody filled
    placeholders — {"title":"value","isbn":"value"} — which a spec requiring
    \d{13} refuses, so asserting 201 against it would have reported a
    contradiction the application never committed.

    FieldConstraintDiscovery reads the constraints the artifact's OWN code
    enforces before it throws (length() > N, a Pattern.compile constant resolved
    to the identifier it is matched against, inline matches("...")).
    RegexSampleGenerator samples a narrow subset and returns empty for
    alternation, negated classes and back-references rather than approximate;
    every sample is verified against its own pattern before return.

    BootGate.Unobserved.BODY_REFUSED is what makes probing safe: a 4xx to the
    ASSERTED request of a success probe is an abstention, not a contradiction —
    the body was derived on this side and no derivation can be sure it satisfies
    validation it never discovered. A 5xx is still reported; that is the
    application breaking, not declining.

    Verified on run 2026-08-23_02-12-34's own artifact: the old placeholder body
    draws 400 (refused, hence silent), the new one draws 200 (accepted), and 200
    against a criterion demanding 201 is what all five failing smoke checks
    report. Replay over 8 preserved trees: 74 body-carrying 2xx criteria all
    abstained before, 61 (82%) probeable now, coverage 71.4% -> 86.3%.

    Field DoD met 3/3 with the rule fixed in advance — each run independently
    produced "POST /loans -> 201, but the running application answered 500".

  For orientation: the change that answered this ticket touched RequestBodySynthesizer. Which classes you change is yours to decide.
  Add the new classes FieldConstraintDiscovery and RegexSampleGenerator in package com.walpro.autobuilder.core.build.

  There is no specification test for the change: write the tests it needs yourself, beside the existing
  ones in src/test/java. The operator will check the change with tests of their own, which call:

    - RegexSampleGenerator.sample(String regex), returning Optional<String>: a value that matches the
      pattern, for patterns built from literal characters, \d, character ranges such as [0-9], [a-z] and
      [a-zA-Z], the quantifiers ?, *, +, {n} and {n,m}, and the anchors ^ and $ -- for example \d+, [a-z]+\d{2},
      a?b, x*y and ^\d{5}$; for \d{13} the value is 0000000000000. Empty, never an approximation, for
      alternation such as (alpha|beta), a negated class such as [^a-z]{3}, a back-reference such as
      (\d{3})-\1, a class such as \p{Alpha}{4}, a malformed pattern such as [ or a lone \, a null or empty
      pattern, and a pattern whose only sample is the empty string, such as x*;
    - FieldConstraintDiscovery.fromSource(String source), returning a Map<String, FieldConstraintDiscovery.Constraint>
      from each checked name to its Constraint, a record of (String regex, Integer maxLength): a Pattern
      constant built with Pattern.compile and matched against a name gives that name the constant's regex,
      the Java string literal unescaped (the source's "\\d{13}" is the regex \d{13}); name.length() > N gives
      maxLength N, and name.length() >= N gives N - 1; an inline name.matches("[a-z]{4}") gives the regex
      [a-z]{4}; two bounds on one name are merged and the tighter one governs (> 40 and >= 10 give 9); a name
      matched against a pattern the source does not declare gets no entry at all;
    - FieldConstraintDiscovery.satisfyingValue(Constraint constraint, String fallback), returning
      Optional<String>: the fallback when the constraint is null; a value that matches the regex when the
      generator can sample it; the fallback cut to the maxLength when there is only a maxLength (value with
      3 gives val); empty when the regex cannot be sampled, and empty when the regex's value is longer than the
      maxLength (\d{13} with 5) -- a value is never cut to fit and so broken;
    - FieldConstraintDiscovery.unescapeJavaLiteral(String text), turning the text of a Java string literal
      into the string it denotes (\\d{13} gives \d{13});
    - RequestBodySynthesizer.candidateBodies(path, artifactRoot), exactly as today;
    - RequestBodySynthesizer.acceptableBody(String path, Path artifactRoot), returning Optional<String>: the
      body candidateBodies derives from the model source that matches the path, with the value of every
      field the artifact's own sources constrain replaced by one that satisfies the constraint -- for a Book
      with title and isbn, and a BookService matching isbn against Pattern.compile("\\d{13}"), the body is
      {"title":"value","isbn":"0000000000000"}; the placeholders unchanged when no constraint is found
      ({"title":"value"}); and empty when any one constrained field cannot be satisfied, when a constrained
      field is not a String (an int copies checked with copies.length() > 3), and when no model source
      matches the path -- never {}, which creates nothing.

  OBJECTIVE: the constraints are discovered, sampled and applied as above, and the whole suite passes.

  DO NOT modify the existing tests under src/test: they are the operator's, and if one of them fails, the
  code is what is wrong. Add your own tests beside them. Keep the project's packages, classes and naming.
