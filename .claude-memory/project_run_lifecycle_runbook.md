**Launch:** `FILE_BASE_PATH=data/firestarter setsid nohup java -jar target/autobuilder-1.0.1-SNAPSHOT.jar --spring.profiles.active=dev-auto > /tmp/autobuilder-stdout.log 2>&1 < /dev/null & disown`. (2026-08-28: forgetting `FILE_BASE_PATH` no longer crashes — the default is the relative `data/firestarter` — but a run should still name its target explicitly so its logs land where the watcher looks.) Rebuild the jar (`mvn package -DskipTests`) after any framework change — the run uses the jar, not the source tree.

**⚠ setsid is NOT optional (burned 2026-07-15):** launching `preflight.sh live` as a harness-tracked background task (run_in_background) looked safe — but when the harness stopped the task it killed the whole process GROUP, taking the nohup'd JVM down mid-run (~19 min in, no terminal, no corpus). nohup does not change the process group. Always `setsid nohup scripts/preflight.sh live 45 > <launchlog> 2>&1 < /dev/null & disown`, then watch for completion with a separate kill-safe loop that only greps the launch log for `PREFLIGHT:` — that watcher dying harms nothing.

**Stop a run on purpose with `scripts/stop_run.sh "<reason>" [run_dir]` (2026-10-17), never a bare kill.** It writes `STOPPED.txt` (time and reason) into the run dir and stops the JVM by the pid preflight now keeps in `jvm.pid`; preflight then ends the run as `terminal=jvm-stopped`, not `jvm-died` (the user: "call it what it is"). field77 was stopped by a bare kill before this existed; its records were corrected by hand. See [[feedback-name-outcomes-for-what-they-are]].

**Stop — the brake/pause trap:** a T4-I brake or SYSTEM_PAUSED terminal pauses the LOOP but keeps the JVM alive, logging "System is paused. Skipping run" every minute and **holding port 8081**. A relaunch then dies at boot with a port conflict (burned 2026-06-12 20:04: silent 15 min before diagnosis). Always kill the old JVM first and confirm: `ss -tln | grep 8081` empty before relaunch.

**Process matching — pgrep self-match:** `pgrep -f "java -jar.*autobuilder"` matches the *calling shell's own wrapper* (it embeds the pattern/launch text) → false "app UP", and `pkill -f` once killed my own command chain mid-pipeline. Reliable liveness: `for p in $(pgrep -x java); do tr '\0' ' ' < /proc/$p/cmdline | grep -q "autobuilder-1.0.1-SNAPSHOT.jar" && echo up; done`. Note `pgrep -x java` also matches the IntelliJ build JVM and neo4j — always confirm via the jar name in cmdline, never kill on a loose match.

**Monitor patterns (what a watcher must catch):** terminal markers vary — `T2-DR: root … marked (COMPLETED|GIVEN_UP)`, `root convergence stall` (live log has SPACES; the signal name `root-convergence-stall` does NOT appear), `Result: GOAL_EXHAUSTED`, `System is paused` (exclude the per-minute "Skipping run" repeats), `exhaustion runaway`. Also watch behaviour.ndjson mtime for silence ≥15 min (8 min is too twitchy — host load spikes legitimately starve the local model for minutes; report `/proc/loadavg` with any silence event to distinguish environment pressure from a wedge) and Neo4j `ServiceUnavailableException` bursts (Docker Desktop backend has crashed under memory pressure and taken the neo4j container with it, 2026-06-12 ~10:50).

See [[project-log-and-backup-conventions]] for which log files to read and [[project-tests-rotate-live-logs]] for why `mvn test` must not run while a run is live.


**⚠ WAITING ON `mvn` BY ITS OWN NAME NEVER MATCHES — fourth variant, 2026-08-24.** `until ! pgrep -f "mvn -o test"; do sleep 30; done` returned IMMEDIATELY and reported an empty result, because `mvn` is a shell script that execs a JVM: the live process is `/usr/bin/java -Djansi.mode=force -classpath …/plexus-classworlds-2.x.jar`, and nothing on the box is named `mvn`. The waiter exited 0 with the suite still running, which looks exactly like a finished suite. **And the obvious replacement SELF-MATCHES — fifth variant, same hour.** `until ! pgrep -f "plexus-classworlds"` never exits, because the waiter's own bash `-c` command line contains that string; `pgrep -af` showed two hits and both were my wrapper shells, with maven already gone. **So the fix for a self-matching pattern must itself be checked for self-matching.** The only reliable forms: match by PID (`kill -0 "$pid"` on a pid the launcher printed), or read `/proc/<pid>/cmdline` for a specific jar as the top of this file already says. **Standing check before arming any liveness loop: run the predicate once while the thing is definitely alive, and once while it is definitely dead.** Both traps here would have been caught in ten seconds by the second half of that check. 

**⚠ SIXTH VARIANT, 2026-08-25 — AND THE FIRST THAT BLOCKED REAL WORK RATHER THAN MISREPORTING.** A background waiter used `until ! pgrep -f "org.codehaus.plexus.classworlds.launcher.Launcher"`, so its OWN command line carried the pattern: it matched itself and could never exit. An A/B series driver then used the same predicate, matched THAT shell, and waited on a process that was only waiting on itself — **two processes deadlocked on a string, with the experiment never starting**. Diagnosis was blocked too, because every check I wrote containing the literal also self-matched; the truth needed enumerating `/proc` and excluding my own shell, then `kill <pid>`.

**The rule, earned six times: a liveness predicate must never be a string the checking command itself contains.** Match by PID (`kill -0 "$pid"` on a pid the launcher printed), or by a marker the watched process writes to a file. `pgrep -f` on a distinctive string is a trap wherever your own tooling echoes that string — which, for an agent that writes its own diagnostics, is always. **Operational corollary while such a loop is armed: do not run ANY command containing the literal, or you re-block it at its next poll.**

**⚠ `pkill -f <pattern>` KILLS YOUR OWN WATCHERS — third variant, 2026-07-30.** The runbook already records `pgrep -f` self-matching the calling shell. The same trap bites `pkill -f` against a *driver script*: a Monitor whose command line contains the pattern (because it greps for the same string) is itself matched and killed — observed killing a monitor mid-series (exit 144), and earlier killing a command chain mid-pipeline. It also bites preflight's own G1 guard, which counted five "live JVMs" that were really monitor shells mentioning the jar name.

**Fifth variant, 2026-09-25: a `ps ... | grep -q <full command>` confirmation does NOT make a `pgrep -f` loop safe.** To restart `early_stop.sh` I looped over `pgrep -f "early_stop\.sh structdiff"` and killed only PIDs whose command line contained `bash scripts/early_stop.sh structdiff` -- my own `bash -c` wrapper contained that exact text, so it passed the check and the shell killed itself (exit 144) after killing the real watcher. Find the target with a split literal (`ps -eo pid,args | grep "early_""stop"`) and kill one explicit PID in a separate call.
**Rule:** never put a process-matching pattern in a command line that also matches it. Either split the literal (`"frozen_ser""ies.sh"`), or scan `/proc/<pid>/cmdline` with a `comm` guard (`[ "$(cat /proc/$p/comm)" = java ]`), which is what `scripts/autobuilder_up.sh` exists for — it holds the jar pattern in a FILE so no caller's command line carries it.
**⚠ A WATCHER CAN GO BLIND WITHOUT SELF-MATCHING — `grep -c … || echo 0` (2026-08-30).** `grep -c` prints `0` AND exits 1 when there are no matches, so `n=$(grep -c PATTERN f || echo 0)` assigns the two-line string `"0\n0"`. Every later `[ "$n" -gt "$prev" ]` then dies with *integer expression expected* and evaluates FALSE — so the watcher reports nothing at exactly the counts where it must report the first occurrence. Caught here only because a periodic tick printed `0\n0 moves` on its own line; the marker checks had been silently inert for the run's first 20 minutes. **Use `c=$(grep -c … 2>/dev/null || true); c=${c:-0}`** — `grep -c` already prints a number, so the fallback only has to survive the exit code. **Standing check, now twice-earned: run the predicate once while the thing is definitely absent AND once while it is definitely present, before trusting a watcher** ([[feedback-monitor-every-terminal]]). The absent case is the one that bites: a watcher that works only after the first match cannot report the first match.

**⚠ EIGHTH VARIANT, 2026-09-02 — THE WATCHER WAS ALIVE THE WHOLE RUN AND EMITTED ZERO BYTES: `awk` IS `mawk`, AND IT BLOCK-BUFFERS ITS *INPUT*.** A `tail -F launch.log applog | awk -f filter.awk` monitor watched a 60-minute run, both processes still alive at the end, output file **0 bytes** — it never reported the `PREFLIGHT:` terminal line that was plainly in the log. Replaying the identical pipeline against the finished file printed it instantly, which is what makes this one so hard to see: **the pipeline is correct; only the streaming case fails.**
- **Mechanism:** on this box `/usr/bin/awk` is **mawk**, which reads its input from a pipe in ~4KB blocks. The launch log accumulated **4515 bytes across the whole hour**, so everything past the first block sat unread in mawk's input buffer forever. A full-file replay exceeds the block and flushes, which is why every after-the-fact test passes.
- **🔴 `fflush()` CANNOT FIX THIS, AND THE TOOL DOCUMENTATION SAYS IT CAN.** The Monitor guidance names `fflush()` as the awk remedy; `fflush()` flushes awk's OUTPUT. Here the record is never READ, so there is nothing to flush. **Correct advice for mawk is `-Winteractive`** (verified: emits immediately). `stdbuf -oL` on `tail` does NOT help — tail was never the buffer (`tail | cat` streams fine).
  - **CORRECTION 2026-09-08: "put `grep --line-buffered` in front of awk" was recorded here as "also verified" and it is WRONG.** Re-measured by `scripts/prove_watcher_streams.sh`: `tail -F f | grep --line-buffered -F PAT | awk '{print}'` stays silent, because grep now emits per line but **mawk is still the last stage reading a pipe in blocks**, so the line sits in mawk's buffer instead of grep's. The grep remedy works only when **grep is the LAST stage** (`tail | grep --line-buffered` passes; the same grep followed by awk fails). The ladder in the script runs both, so the positional distinction is visible rather than inferred. Also measured failing: `stdbuf -i0 -oL awk` (mawk does not take input buffering from stdio). Only two things work here: `-Winteractive`, or dropping awk so grep is last.
- **🔴 AND MY PRE-ARM CHECK PASSED WHILE MISSING IT.** I ran the standing absent-and-present check — but as `printf ... | awk -f filter.awk`, a closed stdin that flushes at EOF. **The predicate was exercised for CONTENT and never for STREAMING.** Extend the standing check: after arming a watcher, append a marker line to the watched file and confirm the notification actually arrives. Content-correct and stream-correct are different properties, and only the second one is what a monitor does for a living.
  - **2026-09-08: this rule now has an actuator — run it, do not recite it.** `scripts/prove_watcher_streams.sh --pipeline 'tail -F {} | awk -f filter.awk'` grows a scratch file, appends ONE SHORT line, and fails the pipeline if nothing is emitted within the deadline. The line is deliberately tiny: a large write exceeds mawk's ~4KB block and flushes, which is exactly why every after-the-fact replay passed. On failure it walks the ladder below automatically (`tail | cat` → `tail | grep --line-buffered` → `grep | awk` → `tail | awk`), names the buffering stage, resolves `awk`, and prints only the fixes it re-measured. Exercised against the 2026-09-02 case: identifies it in ~20s. **Prove the pipeline before arming it against a live run** — this is the one check that a replay can never stand in for.
- **Diagnostic order that found it fast:** `tail | cat` (works → tail is innocent) → `tail | grep --line-buffered` (works) → `tail | awk` (silent → awk is the buffer) → `readlink -f $(which awk)` → mawk.

**⚠ ELEVENTH VARIANT, 2026-09-17 — `behaviour.ndjson` MTIME IS NOT A LIVENESS SIGNAL MID-CYCLE, AND THE SILENCE RULE ABOVE CAN FALSE-POSITIVE ON IT.** The rule above says watch `behaviour.ndjson` for silence >=15 min. During a firestarter run at **load average 175** (a qemu VM, Docker Desktop and Firefox competing with `llama-server`), that file sat **ten minutes stale while the run was perfectly healthy** — `autobuilder.log` had been written 45 seconds earlier. **The two logs have different cadences: the app log streams continuously, `behaviour.ndjson` is written at CYCLE BOUNDARIES**, so under a long model generation its mtime measures cycle length, not liveness. A 15-minute threshold is fine for a fast box and reachable by one slow cycle on a loaded one.
- **Read the app log's mtime for "is it alive", the behaviour log's for "is it making progress".** They answer different questions and only the first is liveness.
- **A single suppressed `ServiceUnavailableException` under saturation is not the Docker-backend crash this runbook warns about.** Distinguish by checking the container (`docker ps`) and the COUNT: the 2026-06-12 crash was a burst with the container gone, this was one line with `neo4j Up 2 weeks` and the JVM still cycling. Report `/proc/loadavg` alongside, as the silence rule already says — at 175 a read timing out is the box, not the database.

**⚠ NINTH VARIANT, 2026-09-03 — THE LIVENESS PATTERN MISSED AN IDE LAUNCH, AND THREE LAUNCHES SILENTLY FAILED TO BIND.** Every liveness check in this repo and in session practice matched `autobuilder-.*-SNAPSHOT\.jar`. An **IntelliJ run configuration launches by CLASSPATH + main class and never mentions the jar**, so a live JVM on port 8081 was invisible: three successive `java -jar` launches died with *Port 8081 was already in use*, `curl --retry` connected to the IDE's OLDER instance, and a new feature "did nothing" for three debugging rounds because the code answering was not the code under test. The class-file bytes proved the deployed jar was correct, which is what finally pointed at the process rather than the build. **This is the same self-match family as the earlier eight, inverted: not a pattern that matches too much, one that matches too little.** Fixed in `preflight.sh`'s G1 gate, which had the same blind spot and was therefore not guarding against an IDE-launched run at all. **Rules: match BOTH forms (`autobuilder-.*-SNAPSHOT\.jar|com\.walpro\.autobuilder\.AutobuilderApplication`), and when a launch is supposed to take a port, CHECK THE LAUNCH LOG FOR `Started AutobuilderApplication` rather than trusting that `curl` reaching the port means your process is the one answering.**

**⚠ TENTH VARIANT, 2026-09-08 — `pgrep -x java` MATCHES THE LOOP'S OWN COMPILE JVMs, so a liveness check can report the run dead while it is cycling.** A waiter used `pgrep -x java | head -1` and declared the run finished; the log kept growing for another sixteen minutes. **The autobuilder loop SPAWNS Maven/compile JVMs for the target project**, so `pgrep -x java` routinely returns several PIDs and `head -1` picks an arbitrary one — usually a short-lived compile that has just exited. This is the ninth variant's "matches too little" inverted into "matches the wrong thing": the pattern is right about the program and wrong about the process. **Rule unchanged and now earned twice: resolve liveness by reading `/proc/<pid>/cmdline` for the jar name (or the main class), never by `pgrep -x java` alone, and never by taking the first PID of several.**

**⚠ `--autobuilder.run.budget-minutes` CAPS THE LOOP, NOT THE JVM (2026-09-08).** A raw `java -jar` launch with that flag was still cycling eighteen minutes into an eight-minute budget, so an `until <jvm gone>; do sleep; done` waiter would have hung forever. **`preflight.sh` kills the JVM at its cap; a hand-rolled launch does not** — the flag governs the loop's own budget accounting. When launching directly (which is the right call for exercising ONE code path on a scratch target), plan to stop the JVM yourself and confirm with the jar-name check plus `ss -tln | grep 8081`. Also seen here: `kill` was not enough for a JVM mid-cycle, `kill -9` was.

**⚠ THE TARGET PROJECT'S BUILD OUTPUT IS IN THE SAME LOG AS THE LOOP'S (2026-09-08).** A monitor grepping `BUILD FAILURE` fired repeatedly on the *target's* compile failures — which are normal evolution activity, the loop working — and read as autobuilder failing. **When filtering a run log for failure signatures, exclude the target's own Maven output** or every grinding run looks like a crash. Narrow the pattern rather than dropping the watch ([[feedback-monitor-every-terminal]]).

**⚠ TWELFTH VARIANT, 2026-09-21 — THE WATCHER WAS POINTED AT THE RIGHT FILE BY THE RIGHT RULE AND STILL BASELINED ON THE PREVIOUS RUN.** A monitor resolving `ls -t data/<target>/logs/autobuilder*.log | head -1` armed about 90 seconds before the new JVM started, so at its first poll the unsuffixed `autobuilder.log` still held the PREVIOUS run's content. It counted that run's 18 probe sweeps, set `prev_probe=18`, and the new run then had to exceed 18 before the watch could emit anything. **The predicate was correct, the file selection rule was correct, and the watch was inert anyway — because a counter-delta watcher takes a BASELINE, and a baseline read from the wrong run is a silence that looks exactly like "nothing has happened yet".**
- **Not the self-match family and not the mawk family:** nothing matched itself, nothing buffered. This is a third mechanism — **a race between arming the watcher and the log rotation that the launch performs.** `ls -t` resolved correctly both before and after; only the CONTENT under the name changed.
- **Fix, and it generalises:** pin the exact file and make the watcher REFUSE TO ARM unless the file is demonstrably this run's — `head -1 "$APP" | grep -q "^$(date +%Y-%m-%d)" || { echo "WATCHER REFUSES TO ARM"; exit 1; }`. A watcher that can tell it is looking at the wrong thing is worth more than one that silently reports zero. Baseline the counters explicitly before arming and print them, so the starting point is visible rather than assumed.
- **Also worth carrying: give the watcher a companion signal that closes the window.** Watching only for the marker cannot distinguish "the mechanism failed to fire" from "the condition never arose". Adding "the first time `mainClass` appears in the tree" — the event that makes the marker impossible — meant silence would have been readable either way ([[feedback-monitor-every-terminal]]).
- **The standing check that would NOT have caught this:** I ran the absent-and-present content check and it passed, because it exercised the PREDICATE, never the BASELINE. Content-correct, stream-correct and baseline-correct are three different properties.

**2026-09-25 -- three tools for runs, all in `scripts/`:**
- **Adopted target run:** move everything but `bootstrap/` aside (`~/.autobuilder/<t>-after-<run>`), restore the pristine tree into `output/` (structdiff: `scripts/extract_structdiff.sh $(cat data/structdiff/bootstrap/origin-rev) data/structdiff/output`; participation: the same with `scripts/extract_participation.sh` and `data/participation`), launch `PREFLIGHT_TARGET=<t> PREFLIGHT_EXTRA_FLAGS="--autobuilder.start.mode=ADOPT_PROJECT" setsid nohup scripts/preflight.sh live 60 ...`, then `scripts/post_adopted_goal.sh <t> data/<t>/bootstrap/seed.txt`. An absent `bootstrap/seed.obligations.txt` is generated at goal-post time (rule:/gate: markers included).
- **`scripts/early_stop.sh <target>`** started beside the run: (since 2026-09-25 it scores a SERVING yardstick through the checkpoint copy built and booted on its own port, and never stops a run whose best is the maximum) every 10 min it scores the newest `checkpoint-archive` entry (NOT the live tree, which holds unmerged candidates during evaluation) with the target's yardstick; after 25 min, 20 min without a better score pauses the loop (`POST /pause`) and preflight records `terminal=operator-stop` and archives as usual. A closure refusal with NEW content restarts the patience clock. It exits by itself when the app is gone.
- **Change target run** (participation-roles/-totals): `scripts/prepare_participation_change.sh <t> data/<t>/output` instead of the extract script; otherwise as an adopted run. **Full suite beside Docker:** `MAVEN_OPTS=-Xmx1g mvn -q install -DargLine=-Xmx3g` -- an uncapped suite once OOM-killed Docker Desktop (the qemu VM carries the highest OOM score).
- **`scripts/merge_lineages.sh <treeA> <labelA> <treeB> <labelB> <child>`** (T4-CS; `--base <tree>` first to merge DIFFERING library code three-way): a child from two lineages over IDENTICAL `src/main` (refused otherwise), test layers merged member by member, the child's suite run as the check, provenance in `MERGE-PROVENANCE.tsv`. Measure first with `scripts/code_lineage_overlap.py <treeA> <seedA> <treeB> <seedB>`.
- **`scripts/bundle.py store|restore|list`** (T4-CR): a phase = sources + bootstrap + meta + checkpoint archive + the lineage subgraph; restore continues the lineage on a database that does not hold it; resume with `CONTINUE_LINEAGE` + `--autobuilder.service.resume-from-preserved=true` (+ `--spring.data.neo4j.uri/password` for another database).
- **A waiter's PID must be the one preflight printed** (`grep -o "pid [0-9]*" <launch log>`): a mistyped PID makes `! kill -0` true at once and the waiter "fires" on a live run.
- **2026-09-26 -- a change target from a REAL ticket** (`criterion-status`): `scripts/prepare_criterion_status_change.sh criterion-status data/criterion-status/output`, yardstick `scripts/smoke_criterion_status.sh` (one check per spec test case, parameterized invocations included). Otherwise as a change-target run. After a Docker OOM kill (the qemu VM goes first) restart with `systemctl --user start docker-desktop`; a run whose Neo4j died aborts every cycle ("Failed to prepare runtime context") -- pause it rather than letting the budget run out.
- **2026-09-26 -- back-to-back runs:** before `951308ef` an `early_stop.sh` watcher only polled the port, so it outlived its run and adopted the next one on the same port. Now bound to the run's own log head; still, check `pgrep -f early_stop.sh` shows one watcher per live run.
- **2026-09-27 -- toy cases are VERSIONED** (`scripts/toycase_version.py`; the user: "we version the toy cases ... so we also have a history what changed regarding the toy cases over time"). Every `data/<t>/bootstrap/` carries `VERSION` + `CHANGELOG.md` (history before 2026-09-27 reconstructed from git, one version per commit). Any change to a bootstrap -- seed, spec, protected paths, briefing, a new origin-rev -- is `toycase_version.py bump <t> --reason "..." [--rev <commit>]`; `--rev` records which module files changed between the revs. Preflight writes `toycase=<t> v<N>` into the run's `target.txt` (archived) and warns on an UNVERSIONED CHANGE. Compare runs only within one toy-case version ([[feedback-dont-evaluate-a-build-with-older-runs]] -- the task is part of "constant"). Loop runs on toy cases are capability measurements, not a ticket's path (M-F).

**2026-10-05, two shell traps met while stopping batches:** `pkill -f '<pattern>'` also kills the shell that runs it (its own command line contains the pattern) -- stop processes by PID from `ps -eo pid,args | grep '[p]attern'`. And a `$` inside a grep pattern is an end-of-line anchor (`grep -c 'early_stop.sh $T 10'` never matches the literal `$T`): use `grep -F` for literal text. A watcher that follows files with `tail -F` missed early_stop's lines once; the batch watchers now poll the files every minute and print what is new.

**2026-10-22, watching a run on the merge canvas:** a canvas served by an Autobuilder app on another port makes preflight refuse the run (G1: any live Autobuilder JVM reads as a run in progress -- by design). During a run, open the canvas on the run's own port (`:8081/merge.html?session=<id>&follow=1`, gone when the run ends) or serve it read-only from outside the JVM (a static server for `src/main/resources/static` plus the session's `graph.json`, which the run's app rewrites after every edit). The run's session id is printed by `prepare_integration_run.sh` before launch.
