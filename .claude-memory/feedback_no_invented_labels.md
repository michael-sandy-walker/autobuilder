Do not invent shorthand labels or role-nouns for structures I created — "arm 1 / arm 2", "arm ON / arm OFF", "phase A–H", "winner/loser", "the keeper", "chain X" — in code identifiers, event fields, roadmap notes, analysis prose, **or scratch/backup file & directory names**. Four incidents: phase letters A–H (2026-06-10, user couldn't find them anywhere because they existed only in my head), "arm 1/arm 2" + "loser" in the T4-AJ Part B ship (2026-06-11), **"keeper" surviving the very fix that removed "loser" the same day**, and **"armON/armOFF" backup dirs + table headers in the 2026-06-18 T4-BQ A/B — the user couldn't decode them 3 days later** (2026-06-21; renamed to `naming-block-enabled` / `naming-block-disabled`). The rule must be checked against *every* coined noun, not just the ones already flagged. **A/B-specific trap:** "ON/OFF" never says *what* is toggled and "arm" is the same vague shorthand — name each configuration by the mechanism's state (*block enabled* / *baseline*), in dir names and column headers alike.

**Relapse 2026-06-22 (caught by user):** days after writing the above, I narrated the test-compile-coupling experiment with "the coupled arm / the decoupled arm" throughout, and named the orchestration script "driver" — both generic jargon, "arm" being the *exact* word already corrected. The rule had been filed but not applied to live wording: it caught the literal string "arm ON/OFF" while bare **"arm"** sailed through. Lesson: **a filed rule you don't check against while composing is decoration.** Avoid the bare words too — "arm" (say "configuration / condition", or just the descriptive name like *coupled* / *decoupled*), "driver" (say "run-batch script" or describe what it does), "harness", "pipeline-stage". Before sending, scan your own draft for any noun standing in for a thing you made and ask whether it names the thing or just tags it.

(And the rule's own wording is in scope: "ban" was reworded out 2026-06-22 at the user's nudge — it's a charged, [[feedback-neutral-vocabulary]] word in a note about choosing precise ones. Every word can be misread; prefer the plain, non-loaded verb — "avoid", "don't use", "prefer" — over "ban".)

**Why:** labels force results into stories. Once a label exists, later analysis reports "arm 2 fired" instead of the underlying fact, which invites omission and hallucination — the narrative layer gets confirmed instead of the data. The user: "It's poisoning the analysis by forcing results into stories."

**How to apply:** name things by what happens to them, preferably with participles or plain descriptions: *the kept goal* (not "the keeper"), *the subsumed goal* (not "the loser"), *the GIVEN_UP-blocker fold* (not "arm 2"). The same applies upward: prefer the concrete artifact over the abstract category — *the criteria list* (not "the evidence"), as the user's own edit of commit 9570f1b's message demonstrated. Test before writing: would the name mean anything to someone who hasn't read this code/conversation? If a group of items needs referring to twice, repeat the description or use the actual identifiers (ticket IDs, class names, event names). Related: [[feedback-neutral-vocabulary]] (contest/courtroom/military words are a special case of the same problem).

Also from the same review (2026-06-11): don't introduce arbitrary small caps that undermine a mechanism's purpose — a "max 4 criteria in the equivalence prompt" cap hid exactly the distinguishing criteria the prompt was added to expose, and the reviewer's top-5 candidate head-cut was the same flaw one layer up (it ranked by a string metric *measured* to misorder exactly the discrimination that matters, so it could drop the true match while keeping lexical noise). Legitimate bounds target the genuinely expensive resource (LLM *call* budgets) or prune with measured margin (a relevance floor where real duplicates score 0.69-0.81 vs a 0.5 cutoff). Fixed-size truncation of evidence, ranked by an unreliable metric, is never a cost optimisation — it's silent evidence loss.
